# 数据模型迁移草案

## 目标

将项目从“B 站 session 即用户身份”的单用户模型，迁移到系统用户、工作区、知识库、内容源绑定四层归属模型。

## 第一阶段新增表

- `system_users`
- `system_sessions`
- `workspaces`
- `workspace_members`
- `knowledge_bases`
- `source_bindings`
- `source_credentials`

## 第一阶段保留表

- `user_sessions`
- `favorite_folders`
- `favorite_videos`
- `video_cache`

这些表先保留用于兼容旧流程。新接口不再把 `user_sessions.session_id` 当作系统用户身份。

## 后续需要补充的归属字段

- `favorite_folders.workspace_id`
- `favorite_folders.knowledge_base_id`
- `favorite_folders.source_binding_id`
- `favorite_videos.knowledge_base_id`
- `video_cache.workspace_id`
- `video_cache.knowledge_base_id`
- `video_cache.source_binding_id`

## 迁移原则

- 新用户注册时自动创建个人工作区。
- 新知识内容入库必须写入 `workspace_id` 和 `knowledge_base_id`。
- B 站账号作为外部内容源绑定到系统用户，不再作为系统身份。
- 旧数据默认视为本地单用户历史数据，不自动暴露给新系统用户。
- 如需导入旧数据，应由用户在管理界面手动选择目标知识库后执行归属迁移。

## 手动迁移建议

1. 创建一个系统用户和默认个人工作区。
2. 创建一个“历史 B 站收藏”知识库。
3. 将旧 `user_sessions` 中有效 B 站登录态迁移为 `source_bindings` 和 `source_credentials`。
4. 将旧收藏夹、视频缓存和向量数据补写 `workspace_id`、`knowledge_base_id`、`source_binding_id`。
5. 抽样验证搜索结果只返回目标知识库内的数据。

## 风险点

- SQLite 适合本地开发，真实多用户部署前建议迁移到 Postgres。
- 旧向量数据缺少范围元数据，不能直接参与多用户检索。
- 加密凭据依赖 `APP_ENCRYPTION_KEY`，生产环境必须固定配置并备份。
