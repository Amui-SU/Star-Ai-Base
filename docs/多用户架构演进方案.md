# Bilibili RAG 多用户架构演进方案

> 目标：将当前“本地单用户 + B 站 session 驱动”的 Bilibili RAG，演进为“系统账号为主、B 站账号为外部内容源”的多用户知识库系统。

## 1. 背景与结论

当前项目已经完成了 B 站扫码登录、收藏夹读取、ASR 转写、向量化入库、Chroma 检索、流式问答、多模型切换等核心能力。它适合作为个人本地工具继续使用，但不适合直接作为多用户 Web 服务上线。

多用户化的核心结论是：

- 系统账号必须成为主身份，不能继续把 B 站 `session_id` 当作应用身份。
- B 站账号只作为外部内容源绑定到系统账号。
- 所有知识库数据、缓存、向量、任务、对话都必须带明确归属。
- 所有查询、检索、删除、清空、统计接口都必须按当前用户和知识库过滤。
- B 站 Cookie、模型 API Key 等敏感凭据必须后端加密保存，不能暴露到前端或日志。

推荐采用“渐进式重构”：先补身份和数据归属，再拆服务边界和后台任务，最后扩展更多内容源。

## 2. 当前架构问题盘点

### 2.1 身份体系

现状：

- `app/routers/auth.py` 通过 B 站扫码创建 `session_id`。
- 前端将 `bili_session` 存入 `localStorage`。
- 后续接口通过 `?session_id=...` 识别用户。
- `user_sessions` 同时承担 B 站登录态、用户信息、系统会话三类职责。

问题：

- `session_id` 是外部账号会话的包装，不是系统账号身份。
- URL query 传递会话 ID 容易出现在日志、浏览器历史和代理记录中。
- 退出登录只清内存，数据库里的 `is_valid` 没有统一失效流程。
- 多用户下无法支持邮箱/密码、第三方登录、角色权限、团队协作等能力。

### 2.2 数据归属

现状：

- `video_cache` 以 `bvid` 全局唯一。
- `favorite_folders` 绑定 `session_id`。
- `favorite_videos` 只关联内部 `folder_id`。
- Chroma 元数据只记录 `bvid`、`title`、`source`、`chunk_index`、`url`。

问题：

- 不同系统用户收藏同一视频时，缓存和向量天然共享，容易产生越权检索。
- 收藏夹按 `session_id` 关联，不适合作为长期数据归属。
- Chroma 检索如果不强制带租户过滤，会跨用户召回内容。
- `/knowledge/stats`、`/chat/search`、`/knowledge/clear`、`/knowledge/video/{bvid}` 等接口没有用户范围。

### 2.3 任务与运行时状态

现状：

- 构建任务保存在 `knowledge.py` 的内存字典 `build_tasks`。
- RAG 服务通过模块级 `_rag_service` 单例持有。
- 构建任务使用 FastAPI `BackgroundTasks`。

问题：

- 服务重启后任务状态丢失。
- 多进程部署时任务状态不一致。
- 用户 A 可以猜测任务 ID 查询用户 B 的任务状态。
- 长任务缺少取消、重试、限流、并发控制、失败归档。

### 2.4 安全与配置

现状：

- B 站 Cookie 明文存入 `user_sessions`。
- LLM 配置接口会写 `.env.local`。
- CORS 为 `allow_origins=["*"]`。
- 日志里可能记录问题、召回片段、视频标题、异常详情。

问题：

- 多用户环境中明文 Cookie 和 API Key 风险很高。
- 在线修改 `.env.local` 不适合多用户，每个用户的模型配置应归属到用户或工作区。
- CORS 生产环境必须限定域名。
- 日志需要脱敏，避免泄露 Cookie、API Key、用户问题和私有知识内容。

## 3. 目标架构

目标结构：

```text
SystemUser
  -> Workspace
    -> WorkspaceMember
    -> KnowledgeBase
      -> SourceBinding(Bilibili)
      -> KnowledgeItem
        -> KnowledgeChunk
      -> IngestionTask
      -> ChatSession
        -> ChatMessage
```

核心原则：

- `SystemUser` 是系统身份主体。
- `Workspace` 是权限边界，可先默认每个用户一个个人工作区。
- `KnowledgeBase` 是知识隔离边界，所有 RAG 操作必须绑定知识库。
- `SourceBinding` 保存用户绑定的 B 站账号和凭据。
- `KnowledgeItem` 表示一个视频、网页、PDF 或其他内容源文档。
- `KnowledgeChunk` 和 Chroma 元数据一一对应，必须带 `knowledge_base_id`。
- `IngestionTask` 记录同步、转写、切片、向量化等异步任务状态。

## 4. 身份与权限设计

### 4.1 系统账号

建议新增：

- `users`
- `user_sessions`
- `workspaces`
- `workspace_members`

第一版可以只实现个人账号，不急着做团队协作，但表结构应预留 `workspace`。

建议字段：

```text
users
- id
- email
- password_hash
- display_name
- avatar_url
- status
- created_at
- updated_at

user_sessions
- id
- user_id
- session_token_hash
- expires_at
- revoked_at
- created_at
- last_seen_at

workspaces
- id
- name
- owner_user_id
- created_at
- updated_at

workspace_members
- id
- workspace_id
- user_id
- role
- created_at
```

认证方式建议：

- 后端颁发 HttpOnly Secure Cookie 保存系统登录态。
- 前端不再把系统身份令牌放入 `localStorage`。
- API 使用依赖注入获取 `current_user` 和 `current_workspace`。
- B 站 `session_id` 从业务接口中移除，改为选择某个已绑定的 `source_binding_id`。

### 4.2 权限规则

第一版角色可以保持简单：

```text
owner: 拥有工作区全部权限
member: 可查看和使用知识库
```

所有接口必须遵守：

- 读取知识库：当前用户必须属于目标工作区。
- 入库任务：当前用户必须有目标知识库写权限。
- 删除内容：当前用户必须有目标知识库写权限。
- 清空知识库：仅 owner 或知识库管理员可执行。
- B 站凭据：只能由凭据所属用户使用，默认不允许同工作区成员共享 Cookie。

## 5. B 站账号绑定设计

当前 B 站扫码登录流程应改为“绑定外部账号”。

建议新增：

```text
source_bindings
- id
- user_id
- workspace_id
- source_type
- external_account_id
- external_account_name
- external_avatar_url
- credential_id
- status
- created_at
- updated_at
- last_verified_at

source_credentials
- id
- user_id
- source_binding_id
- encrypted_payload
- encryption_version
- expires_at
- revoked_at
- created_at
- updated_at
```

`source_type` 第一版为 `bilibili`，后续可以扩展 `web`、`pdf`、`youtube`、`wechat_article`。

B 站 Cookie 保存规则：

- `SESSDATA`、`bili_jct`、`DedeUserID` 必须加密后保存。
- 解密只发生在后端服务层。
- 日志中严禁打印 Cookie 原值。
- 绑定失效后将 `source_bindings.status` 标记为 `expired` 或 `revoked`。

```text
- external_id

- description
- owner_name
- owner_external_id

- content
- content_source
- status

- updated_at

knowledge_chunks
- id
- workspace_id
- knowledge_base_id
- knowledge_item_id
- chunk_index
- content_hash
- token_count
- vector_id
- created_at

source_collections
- id
- workspace_id
- knowledge_base_id
- source_binding_id

source_collection_items
- id

```

`video_cache` 可以逐步迁移为 `knowledge_items`。如果要复用同一个 B 站视频的转写结果，应显式设计公共缓存层，而不是让业务知识库天然共享。

### 6.2 Chroma 元数据

现有向量元数据：

```text
bvid, title, source, chunk_index, url
```

多用户后必须扩展为：

```text
workspace_id
knowledge_base_id
knowledge_item_id
source_type
external_id
chunk_index
title
url
content_source
```

检索时必须强制过滤：

```text
where = {
  "workspace_id": current_workspace_id,
  "knowledge_base_id": selected_knowledge_base_id
}
```

如果用户限定某个收藏夹或视频，再叠加 `source_collection_id` 或 `knowledge_item_id` 过滤。

## 7. 接口改造方向

### 7.1 认证接口

新增系统认证：

```text
POST /auth/register
POST /auth/login
POST /auth/logout
GET  /auth/me
```

B 站绑定改为：

```text
GET  /sources/bilibili/qrcode
GET  /sources/bilibili/qrcode/poll/{qrcode_key}
GET  /sources/bilibili/bindings
DELETE /sources/bilibili/bindings/{binding_id}
```

### 7.2 收藏夹接口

由 `session_id` 改为 `source_binding_id`：

```text
GET /sources/bilibili/bindings/{binding_id}/favorites
GET /sources/bilibili/bindings/{binding_id}/favorites/{media_id}/videos
```

后端需要校验：

- 当前用户拥有该 `source_binding_id`
- 该绑定状态有效
- 目标知识库属于当前工作区

### 7.3 知识库接口

建议改为知识库范围：

```text
GET    /knowledge-bases
POST   /knowledge-bases
GET    /knowledge-bases/{kb_id}/stats
POST   /knowledge-bases/{kb_id}/sources/bilibili/sync
POST   /knowledge-bases/{kb_id}/ingestion-tasks
GET    /knowledge-bases/{kb_id}/ingestion-tasks/{task_id}
DELETE /knowledge-bases/{kb_id}/items/{item_id}
DELETE /knowledge-bases/{kb_id}
```

不应再有全局 `/knowledge/clear`。

### 7.4 对话与检索接口

建议改为：

```text
POST /knowledge-bases/{kb_id}/chat
POST /knowledge-bases/{kb_id}/chat/stream
POST /knowledge-bases/{kb_id}/search
GET  /knowledge-bases/{kb_id}/chat-sessions
GET  /knowledge-bases/{kb_id}/chat-sessions/{chat_session_id}
```

`ChatRequest` 不再携带 `session_id`，而由系统登录态提供用户身份。

## 8. 后台任务设计

当前 `build_tasks` 内存字典应迁移为数据库表，第一版可继续使用 FastAPI `BackgroundTasks`，但任务状态必须持久化。

建议新增：

```text
ingestion_tasks
- id
- workspace_id
- knowledge_base_id
- source_binding_id
- created_by
- task_type
- status
- progress
- current_step
- total_items
- processed_items
- success_items
- failed_items
- error_message
- started_at

- created_at
- updated_at

ingestion_task_items
- id
- task_id
- knowledge_item_id
- external_id
- title
- status
- error_message

```

任务状态：

```text

```

后续如果要正式部署，再引入 Redis + Celery、RQ、Dramatiq 或 Arq。

## 9. 服务层封装方向

建议将当前服务拆成更清晰的接口：

```text
app/domain/
  auth/
  workspace/
  source/
  knowledge/
  rag/
  ingestion/

app/adapters/
  bilibili/
  vectorstores/
  llm/
  asr/

app/repositories/
  users.py
  knowledge_bases.py
  source_bindings.py
  ingestion_tasks.py
```

内容源统一接口：

```python
class SourceAdapter:
    source_type: str

    async def validate_binding(self, credential) -> dict:
        ...

    async def list_collections(self, binding) -> list[dict]:
        ...

    async def list_items(self, binding, collection_id: str) -> list[dict]:
        ...

    async def fetch_item_content(self, binding, item_id: str) -> dict:
        ...
```

B 站模块只实现这个接口，不直接控制知识库、任务、向量库。

## 10. 安全整改清单

必须优先处理：

- 系统登录态使用 HttpOnly Cookie。
- 禁止在 query string 中传递系统身份凭证。
- B 站 Cookie 和模型 API Key 加密存储。
- 日志脱敏：Cookie、API Key、Authorization、用户私有内容不落日志。
- CORS 改为生产域名白名单。
- 所有删除和清空接口加权限校验。
- 所有检索接口强制带 `workspace_id` 和 `knowledge_base_id` 过滤。
- 限制单用户并发入库任务数量。
- 限制单次收藏夹入库视频数，避免费用失控。
- 对 ASR、Embedding、LLM 调用做用量记录。

## 11. 分阶段路线图

### 阶段 0：冻结边界与补文档

目标：不急着改代码，先明确多用户目标和迁移顺序。

任务：

- 完成本文档。
- 补 `API 接口改造草案`。
- 补 `数据模型迁移草案`。
- 标记现有全局接口风险。

### 阶段 1：新增系统账号与工作区

目标：让系统拥有自己的用户身份。

任务：

- 新增 `users`、`user_sessions`、`workspaces`、`workspace_members`。
- 实现注册、登录、退出、`/auth/me`。
- 引入 `get_current_user` 依赖。
- 前端新增系统登录页。
- 保留旧 B 站扫码流程，但不再把它当系统登录。

### 阶段 2：B 站账号改为外部绑定

目标：把 B 站 Cookie 从系统会话中剥离。

任务：

- 新增 `source_bindings`、`source_credentials`。
- 改造 B 站扫码为绑定流程。
- 凭据加密保存。
- 收藏夹接口从 `session_id` 改为 `binding_id`。

### 阶段 3：知识库数据归属改造

目标：所有业务数据有明确归属。

任务：

- 新增 `knowledge_bases`。
- 将 `video_cache` 迁移或映射为 `knowledge_items`。
- 将收藏夹表迁移为 `source_collections`。
- 所有查询加 `workspace_id` / `knowledge_base_id`。

### 阶段 4：向量库隔离改造

目标：RAG 检索不跨用户泄露。

任务：

- Chroma 写入元数据补 `workspace_id`、`knowledge_base_id`、`knowledge_item_id`。
- `RAGService.search()` 强制接收权限范围。
- 废弃无范围的 `search(query, k)`。
- 清空/删除接口只作用于当前知识库。

### 阶段 5：任务持久化

目标：入库任务可恢复、可追踪、可限流。

任务：

- 新增 `ingestion_tasks`、`ingestion_task_items`。
- 替换内存 `build_tasks`。
- 任务状态接口按当前用户和知识库校验。
- 加入失败重试和任务取消。

### 阶段 6：服务层重构与内容源扩展

目标：让 B 站成为一个可替换 Adapter。

任务：

- 抽象 `SourceAdapter`。
- 拆分 B 站抓取、内容标准化、入库、向量化。
- 为 PDF、网页、手动笔记预留接入点。

## 12. 第一批建议改动

优先级最高的代码改动：

1. 新增系统账号表和登录态。
2. 新增 `source_bindings`，把 B 站扫码改成绑定。
3. 新增 `knowledge_bases`，让问答、搜索、统计都进入知识库范围。
4. 改造 Chroma 元数据和 `RAGService.search()`，禁止无范围检索。
5. 废弃全局清空和全局删除接口。

这五步完成后，项目才算具备多用户化的安全底座。

## 13. 暂不建议做的事

短期不建议：

- 立刻接入团队协作的复杂权限。
- 立刻接入多个内容平台。
- 立刻换掉 Chroma。
- 立刻引入复杂微服务。
- 在身份和数据隔离完成前继续堆 UI 功能。

当前最关键的是把“谁的数据、谁能查、谁能删、向量属于哪个知识库”这些边界固定下来。

## 14. 验收标准

第一轮多用户底座完成后，应满足：

- 用户 A 无法读取、检索、删除用户 B 的知识库。
- 用户 A 的 B 站 Cookie 不会被用户 B 使用。
- Chroma 检索必须带知识库过滤条件。
- 所有任务状态只能被任务所属用户查看。
- `.env.local` 不再保存用户级模型配置。
- 删除知识库只删除当前知识库的数据和向量。
- 日志不包含 Cookie、API Key、系统登录令牌。
